### 1.2 仁归的诞生

**仁归**诞生于一个简单的信念：

> **在这个所有数据都被收集、所有服务都要注册的时代，人们需要一个"什么都不收集、什么都不要求"的安静角落。**

它不是任何公司的产品，不是任何机构的项目，而是一个由**社区共同守护的公共品**。如同公园、图书馆、清晨的街道——它属于每一个愿意珍惜它的人。

### 1.3 仁归的核心理念

| 理念 | 含义 |
|------|------|
| **开源不藏私** | 每一行代码都可被审查、修改、分发 |
| **数据只存本地** | 用户的心灵旅程只属于自己 |
| **治愈优先于功能** | 每个功能都要回答"这是否让用户感到被理解" |
| **拒绝商业化滥用** | 不设付费墙、不接广告、不推销课程 |
| **技术向善** | 科技的意义是温暖与陪伴，而非疏离 |

### 1.4 仁归不是什么

- ❌ 不是医疗机构 — 不提供诊断和治疗
- ❌ 不是心理咨询平台 — 不提供专业咨询服务
- ❌ 不是AI大模型产品 — 基于规则引擎，不调用任何云端AI
- ❌ 不是商业公司 — 没有盈利模式，没有KPI
- ❌ 不是数据平台 — 不收集任何用户数据

## 二、权利体系

### 2.1 用户的权利（User Rights）

| 权利 | 说明 | 实现方式 |
|------|------|---------|
| **数据主权** | 所有数据仅存于用户浏览器localStorage | 代码层面零网络请求 |
| **知情权** | 所有代码开源，可审查每一行逻辑 | GitHub公开仓库 |
| **删除权** | 随时清除浏览器数据即完全删除 | 无需任何审批 |
| **修改权** | 可自由修改源代码 | MIT许可 |
| **分发权** | 可分享给他人，需保留开源许可 | MIT许可 |
| **拒绝权** | 随时停止使用，无任何锁定 | 零注册、零绑定 |
| **不被打扰权** | 不接收任何推送、广告、营销 | 无服务器、无通知 |

### 2.2 项目的权利（Project Rights）

| 权利 | 说明 |
|------|------|
| **方向决定权** | 核心维护者与社区共同决定项目发展方向 |
| **拒绝权** | 拒绝任何可能违背开源誓约的贡献或合作 |
| **版本迭代权** | 在遵守誓约的前提下自由迭代 |
| **品牌保护权** | 防止"仁归"名称被滥用于违背誓约的场景 |

### 2.3 贡献者的权利（Contributor Rights）

| 权利 | 说明 |
|------|------|
| **署名权** | 代码贡献将被记录在CONTRIBUTORS.md |
| **参与决策权** | 可参与讨论、投票、提出建议 |
| **自由退出权** | 随时停止贡献，无任何义务 |
| **知识产权保留** | 贡献者保留自己代码的著作权，仅授予项目MIT许可使用 |

### 5.2 MIT许可对用户/贡献者/项目的意义

| 利益相关方 | MIT许可允许 | MIT许可不允许 |
|-----------|------------|--------------|
| **用户** | ✅ 自由使用 ✅ 自由修改 ✅ 自由分发 | ❌ 无法追责项目方（无担保） |
| **贡献者** | ✅ 保留署名 ✅ 自由贡献 | ❌ 不能限制他人使用自己的贡献 |
| **项目** | ✅ 社区共建 ✅ 代码透明 | ❌ 无法防止他人闭源分支 |

### 5.3 为什么选择MIT而非GPL

| 对比 | MIT | GPL |
|------|-----|-----|
| 修改后可闭源 | ✅ 允许 | ❌ 不允许 |
| 商业使用 | ✅ 完全自由 | ⚠️ 需开源 |
| 传播范围 | 最广 | 受限 |
| 适合仁归的原因 | 让善意传播最远，不设置法律障碍 | — |

**仁归选择MIT的理由**：我们相信善意不需要法律强制。如果有人愿意用仁归的代码做更好的事，我们祝福他。

## 六、社区共建

### 6.1 社区结构
仁归社区
├── 核心维护者（Core Maintainers）
│ └── 负责代码审查、版本发布、方向把控
├── 贡献者（Contributors）
│ └── 提交代码、翻译、文档、设计
├── 测试者（Testers）
│ └── 报告Bug、提出建议、体验反馈
├── 传播者（Advocates）
│ └── 分享仁归给需要的人
└── 用户（Users）
└── 使用仁归，提供真实反馈

text

### 6.2 社区沟通渠道

| 渠道 | 用途 | 状态 |
|------|------|------|
| GitHub Issues | Bug报告、功能建议 | ✅ 推荐 |
| GitHub Discussions | 社区讨论、问题交流 | ✅ 推荐 |
| Pull Requests | 代码贡献 | ✅ 推荐 |
| 邮件列表 | 重要公告 | 🔜 规划中 |
| 即时通讯群 | 日常交流 | 🔜 规划中 |

### 6.3 社区行为准则

1. **善意优先**：假设他人的出发点是善意的
2. **尊重差异**：不同文化、不同观点都应被尊重
3. **不推销**：不在社区中推销任何商业产品
4. **不伤害**：不发布任何可能伤害他人的内容
5. **保持专注**：讨论内容与仁归相关
6. **保护隐私**：不在社区中公开他人隐私信息

## 七、贡献者指南

### 7.1 如何成为贡献者
步骤1：使用仁归
步骤2：发现问题或想到改进
步骤3：在GitHub上创建Issue描述
步骤4：Fork仓库
步骤5：创建分支：feature/你的功能名
步骤6：编写代码并测试
步骤7：提交Pull Request
步骤8：等待核心维护者审核
步骤9：合并后，你成为贡献者！

text

**提交 PR 前，请先阅读并同意 [贡献者许可协议（CLA）](../CLA.md)。**

### 7.2 贡献类型

| 贡献类型 | 适合人群 | 示例 |
|---------|---------|------|
| **代码贡献** | 开发者 | 新增游戏、修复Bug、优化性能 |
| **翻译贡献** | 多语言能力者 | 翻译页面、文档、文化内容 |
| **内容贡献** | 心理学/文学爱好者 | 扩充AI回应库、古诗词库 |
| **设计贡献** | 设计师 | UI/UX改进、图标设计 |
| **测试贡献** | 所有用户 | 报告Bug、提出建议 |
| **传播贡献** | 所有用户 | 分享仁归给需要的人 |

### 7.3 贡献者署名

所有贡献者的名字将记录在项目根目录的 [`CONTRIBUTORS.md`](../CONTRIBUTORS.md) 文件中。

### 7.4 贡献者福利

| 福利 | 说明 |
|------|------|
| 署名权 | 名字记录在 CONTRIBUTORS.md |
| 决策参与 | 可参与项目方向讨论 |
| 优先级 | 你的 Issue 和 PR 将被优先处理 |
| 社区认可 | 在社区中获得尊重 |

### 7.5 贡献者守则

1. **代码必须通过伦理审核**：新功能需回答"这是否治愈？是否安全？是否尊重隐私？"
2. **不引入外部依赖**：保持纯前端、零依赖
3. **不添加追踪代码**：任何数据收集代码都会被拒绝
4. **测试后再提交**：确保功能正常运行
5. **文档同步更新**：新功能需同步更新文档

## 八、争议解决

### 8.1 决策流程
提出议题 → 社区讨论 → 核心维护者评估 → 社区投票（如有必要）→ 做出决定

text

### 8.2 分歧处理

| 分歧类型 | 处理方式 |
|---------|---------|
| 技术分歧 | 以代码质量为标准，核心维护者最终决定 |
| 伦理分歧 | 以开源誓约为标准，不可妥协 |
| 方向分歧 | 社区讨论+投票 |
| 个人冲突 | 私下沟通解决，不在社区公开 |

### 8.3 退出机制

任何贡献者可以随时退出。退出时：

- ✅ 保留已贡献代码的署名权
- ✅ 可以创建自己的分支（Fork）
- ❌ 不得带走社区共识和品牌资产
